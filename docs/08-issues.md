# 8장. 좋은 Issue 작성법

> **이 장을 다 읽으시면**
> - Issue 가 단순한 "버그 접수함" 이 아니라 **할 일 관리**의 중심 도구임을 이해하시게 됩니다.
> - 읽고 반응하기 좋은 Issue 제목·본문을 구성하실 수 있습니다.
> - 라벨(Label), 마일스톤(Milestone), Assignee 를 적절히 활용하실 수 있습니다.
> - Issue와 Pull Request를 `Closes #12` 로 연결하실 수 있습니다.
> - 팀 프로젝트에서 Issue 로 **주간 할 일**을 관리하는 예시를 보시게 됩니다.

---

## 8.1 Issue는 생각보다 많은 일을 합니다

많은 분들이 Issue를 "버그 신고 게시판" 으로만 알고 계십니다. 하지만 Issue는 GitHub 협업의 **공식 회의록**에 가깝습니다.

- 🐛 **버그 리포트**: "이런 상황에서 이런 에러가 납니다."
- ✨ **기능 제안**: "이런 기능이 있으면 좋겠어요."
- 📋 **할 일 관리**: "이번 주에 할 일 10가지" 를 Issue 로 쪼개 관리
- ❓ **질문 / 논의**: "이 설계, 이렇게 가는 게 맞을까요?"
- 📚 **문서 개선**: "README에 이 부분이 빠져 있어요."

정리하자면:

> **Issue는 "PR로 해결되기 전의 모든 이야기"** 를 담는 공간입니다.

## 8.2 Issue 만들기

저장소의 **Issues** 탭 → **New issue** 를 누릅니다. 저장소에 **이슈 템플릿**이 설정되어 있다면 종류를 고르는 화면이 먼저 뜹니다. 없으면 빈 화면이 바로 열립니다.

적어야 할 항목:

- **Title**: 한 줄 요약
- **Description**: 본문 (아래 섹션에서 템플릿을 드립니다)
- **Assignees** (오른쪽 사이드바): 이 일을 책임질 사람
- **Labels**: 분류
- **Projects / Milestones**: 큰 단위 묶음에 속한다면 지정

## 8.3 좋은 Issue 제목

PR 제목과 기본 감각은 같습니다. "무엇이 문제/해야 할 일인가" 를 **명사로** 짧게 요약하세요.

| 나쁜 예 | 좋은 예 |
| --- | --- |
| `안 돼요` | `[Bug] 로그인 시 빈 비밀번호를 입력하면 500 에러` |
| `질문` | `[Question] 팀프 배포는 어떤 방식으로 할까요?` |
| `할 일` | `[Task] 회원가입 화면에 약관 동의 추가` |

제목 앞의 `[Bug]`, `[Task]` 같은 접두어는 꼭 필요한 건 아니지만, **라벨이 없는 저장소에서** 눈에 잘 띄게 해 줍니다.

## 8.4 좋은 Issue 본문 — 4가지 블록

아래 4개 블록만 기억하시면 됩니다. 상황에 맞게 쓰지 않을 블록은 지우셔도 됩니다.

### 버그 리포트 템플릿

```markdown
## 배경
- 어떤 기능을 사용하다가 발생했는지

## 재현 방법
1. `/login` 페이지로 이동
2. 이메일: `test@example.com`, 비밀번호: (공란)
3. [로그인] 버튼 클릭

## 기대했던 동작
"비밀번호를 입력해 주세요" 경고가 떠야 합니다.

## 실제 동작
500 Internal Server Error 페이지가 보입니다. 콘솔 에러 로그:
```
TypeError: Cannot read properties of undefined (reading 'length')
    at validatePassword (auth.js:42)
```

## 환경
- OS: macOS 14.5
- 브라우저: Chrome 124
- 커밋: `a1b2c3d` (main)
```

### 기능 제안 템플릿

```markdown
## 왜 필요한가요?
사용자가 자기 프로필을 수정하려면 현재는 관리자에게 요청해야 합니다. 불편함이 많습니다.

## 제안하는 기능
- 프로필 설정 페이지에서 닉네임과 자기소개를 직접 수정

## 대안
- 관리자 페이지에 "대신 수정" 기능만 추가하는 방법도 있지만, 번거로움은 비슷합니다.

## 참고 자료
- 비슷한 UI: https://...
```

### 할 일 / 태스크 템플릿

```markdown
## 목표
이번 주까지 로그인 기능을 완성한다.

## 체크리스트
- [ ] 로그인 UI 작성 (#15)
- [ ] 인증 API 연결 (#16)
- [ ] 로그인 실패 에러 처리
- [ ] 테스트 코드 작성

## 참고
- 디자인: Figma 링크
- API 명세: Notion 링크
```

**좋은 Issue의 핵심 질문 3가지** 를 늘 염두에 두세요.

1. 무엇이 문제인가? (**재현 가능**한가?)
2. 내가 기대한 동작은?
3. 내 환경은?

## 8.5 라벨(Labels) 활용법

라벨은 Issue 를 **색깔별로 분류**하는 기능입니다. 저장소를 만들면 기본 라벨이 몇 개 들어 있고, `Issues → Labels` 탭에서 추가/삭제하실 수 있습니다.

학부 팀 프로젝트에 유용한 라벨 묶음을 예시로 드립니다.

| 색 | 이름 | 의미 |
| --- | --- | --- |
| 🔴 | `bug` | 동작이 잘못된 문제 |
| 🟢 | `enhancement` / `feature` | 새 기능 |
| 🔵 | `documentation` | 문서 |
| 🟡 | `question` | 질문/논의 |
| ⚪ | `good first issue` | 신규 기여자에게 추천 |
| 🟣 | `help wanted` | 도움이 필요함 |
| 🟠 | `priority: high` | 우선순위 표시 |

색깔을 일관되게 쓰시면, **Issues 탭만 봐도** 프로젝트 상태가 한눈에 들어옵니다.

## 8.6 Assignee, Milestone, Projects

- **Assignee**: 누가 이 일을 맡을지. 보통 **Issue 당 1명** 을 권장드립니다. 책임이 분산되면 아무도 안 하는 상황이 생깁니다.
- **Milestone**: "1주차 과제", "중간고사 전 릴리즈" 같은 **시점**을 묶는 도구. `Issues → Milestones` 에서 만드실 수 있습니다.
- **Projects**: 칸반 보드(To Do / In Progress / Done) 를 제공합니다. 팀 과제 진행 상황을 시각화하기 좋습니다.

## 8.7 Issue와 PR 연결하기

PR 본문이나 커밋 메시지에 아래 키워드를 쓰시면, **PR 이 머지되는 순간 해당 Issue 가 자동으로 닫힙니다**.

- `Closes #12`
- `Fixes #42`
- `Resolves #7`

`#숫자` 는 **같은 저장소의 Issue 번호** 를 가리킵니다. GitHub가 자동으로 링크로 만들어 줍니다.

```markdown
## 무엇을 했나요?
- 로그인 시 빈 비밀번호를 받지 않도록 유효성 검사 추가

Closes #42
```

만약 **자동으로 닫고 싶지 않고 연결만** 하고 싶다면 `Related to #42` 처럼 써 주시면 됩니다.

## 8.8 팀 프로젝트에서 Issue 로 일하는 예시

실습 중인 팀 저장소 `team-final-project` 가 있다고 가정하겠습니다.

**월요일 회의**

- 이번 주 목표: "로그인 기능 완성"
- Milestone `Week 3 — Login` 생성
- Issue 를 다음과 같이 쪼개어 만듭니다.
  - `#21 [Task] 로그인 UI 컴포넌트 작성` (Assignee: 지우, Label: `frontend`)
  - `#22 [Task] 인증 API 연결` (Assignee: 상훈, Label: `backend`)
  - `#23 [Bug] 회원가입 이메일 중복 체크 누락` (Assignee: 민아, Label: `bug`)

**작업 중**

- 각자 Issue 번호가 붙은 브랜치를 만듭니다. 예: `feature/21-login-ui`
- PR 본문에 `Closes #21` 을 적습니다.

**주 중 리뷰**

- Pull requests 탭과 Issues 탭이 **진행 상황판** 역할을 합니다.
- 대화가 필요한 주제는 **해당 Issue 에 댓글**로 이어갑니다. 카카오톡과 달리 나중에 찾기 쉽습니다.

**주말 회고**

- Milestone 진행률(`5 of 7 closed`)을 보며 이번 주를 돌아봅니다.
- 못 끝낸 Issue 는 다음 Milestone 으로 옮깁니다.

이 흐름을 한 학기만 유지하셔도, 이력서에 쓸 수 있는 **협업 경험**이 자연스럽게 쌓입니다.

## 8.9 Issue 템플릿으로 팀 규칙 만들기 (살짝만)

저장소 루트에 `.github/ISSUE_TEMPLATE/` 폴더를 만들고 그 안에 `bug_report.md` 같은 파일을 두시면, **New issue** 를 누를 때 템플릿 선택 화면이 뜹니다. 기본 내용이 자동으로 채워지기 때문에, 팀원들이 **꼭 적어야 할 항목을 빠뜨리지 않게** 도와줍니다.

간단한 예시 (`bug_report.md`):

```markdown
---
name: 버그 리포트
about: 동작이 잘못된 부분을 알려 주세요
title: "[Bug] "
labels: bug
assignees: ''
---

## 재현 방법

## 기대했던 동작

## 실제 동작

## 환경
- OS:
- 브라우저/버전:
```

세부 설정은 신입생 단계에서 필수는 아닙니다. 팀이 커지거나 기여자가 늘어날 때 도입하셔도 충분합니다.

---

## 자주 겪는 어려움

- **"질문은 Issue 에 올려도 되나요?"**
  저장소에 따라 다릅니다. 많은 오픈소스는 **Discussions** 탭이나 외부 포럼을 권장하고, 버그/기능만 Issue 로 받습니다. `CONTRIBUTING.md` 를 먼저 확인해 주세요. 팀 내부 저장소라면 Issue 에 올려도 괜찮습니다.
- **"Issue 번호가 너무 커져요."**
  Issue 와 PR은 **번호를 공유**합니다. Issue #43 다음에 PR 하나가 열리면 그 PR 번호는 #44 가 됩니다. 신경 쓰지 않으셔도 됩니다.
- **"실수로 Issue 를 닫았는데 다시 열고 싶어요."**
  Issue 하단의 **Reopen issue** 버튼으로 언제든 되살릴 수 있습니다.
- **"Assignee 를 여러 명 지정해도 되나요?"**
  기술적으로는 가능합니다. 다만 **누가 책임자인가**가 모호해지기 쉬우니, 팀 내부 규칙으로 "1 Issue 1 Assignee" 를 권장드립니다.
