# 5장. Pull Request와 코드 리뷰

> **이 장을 다 읽으시면**
> - Pull Request(PR)가 왜 필요한지, 로컬 `merge` 와 어떻게 다른지 설명하실 수 있습니다.
> - GitHub 웹에서 PR을 만들고 리뷰어를 지정하실 수 있습니다.
> - 좋은 PR 제목·본문을 쓰는 감을 잡으시게 됩니다.
> - 리뷰를 **받는 사람**과 **해 주는 사람**이 지켜야 할 기본 예절을 아시게 됩니다.
> - 리뷰 후 추가 커밋을 올려 PR을 마무리하는 흐름을 익히시게 됩니다.

---

## 5.1 Pull Request는 왜 필요한가요?

4장에서 `git merge` 로 브랜치를 로컬에서 직접 합치는 방법을 배우셨습니다. 그런데 실무나 팀 프로젝트에서는 로컬 merge 대신 **Pull Request(PR)** 를 씁니다. 이유가 있습니다.

- **리뷰 기회**: 합치기 전에 동료가 코드를 읽고 의견을 남깁니다. 버그나 더 나은 방법을 발견하기 쉽습니다.
- **기록**: 왜 이 변경이 필요했는지, 어떤 논의가 오갔는지 **영구히 보관**됩니다. 3개월 뒤 "이 코드 왜 이래?" 라고 물을 때 PR 하나만 열어 보면 맥락이 보입니다.
- **자동 검증**: 테스트나 코드 스타일 검사를 PR 단계에서 자동으로 돌릴 수 있습니다(GitHub Actions 등).
- **권한 분리**: `main` 에 **직접 push 할 수 없게** 설정해 두면, 실수로 망가진 코드가 배포되는 일을 막을 수 있습니다.

한 문장으로 말씀드리면 이렇습니다.

> **Pull Request는 "제가 만든 브랜치를 `main` 에 합쳐도 될까요?" 하고 팀원에게 공식적으로 요청하는, GitHub의 토론·리뷰 공간입니다.**

## 5.2 PR을 만들기 전에 준비할 것

이미 [4장](./04-branches.md)에서 기능 브랜치를 만들고 push 까지 하셨다면 절반은 끝났습니다. 준비물을 정리해 드리면 이렇습니다.

1. `main` 에서 갈라져 나온 **작업용 브랜치** (예: `feature/login`)
2. 그 브랜치에 쌓인 **의미 있는 단위의 커밋들**
3. 브랜치가 **원격(GitHub)** 에 push 되어 있어야 합니다.

마지막 준비를 명령으로 확인해 보겠습니다.

```bash
$ git switch feature/login
$ git status          # 커밋되지 않은 변경이 없는지 확인
$ git push -u origin feature/login   # 아직 원격에 없다면
```

## 5.3 웹에서 PR 만들기

브랜치를 push 하신 뒤 GitHub 저장소 페이지로 가시면, 위쪽에 노란색 배너로 다음과 같은 안내가 뜹니다.

> *feature/login* had recent pushes — **Compare & pull request**

그 버튼을 누르시면 PR 작성 화면으로 넘어갑니다. 만약 배너가 보이지 않으시면 저장소 페이지 상단의 **Pull requests** 탭 → **New pull request** 를 누르셔도 됩니다.

PR 작성 화면에서 확인하실 항목입니다.

| 항목 | 설명 |
| --- | --- |
| **base** | 합쳐질 대상 브랜치. 보통 `main` 입니다. |
| **compare** | 합치고 싶은 내 작업 브랜치. 예: `feature/login` |
| **Title** | 한 줄 요약. 커밋 메시지 형식과 비슷하게 써 주시면 됩니다. |
| **Description** | 변경 배경, 내용, 확인 방법, 관련 이슈 등을 적는 본문. |
| **Reviewers** | 리뷰를 부탁드릴 팀원 |
| **Assignees** | 이 작업을 책임지는 사람 (보통 본인) |
| **Labels** | `bug`, `enhancement`, `documentation` 같은 분류 꼬리표 |
| **Linked issues** | 관련 이슈 번호(8장에서 다룹니다) |

## 5.4 좋은 PR 제목과 본문 쓰기

PR은 **읽는 사람이 최소한의 질문으로 "승인" 버튼을 누를 수 있도록** 구성되어야 합니다.

### 제목

커밋 메시지와 같은 감각으로 쓰시면 됩니다.

- 나쁜 예: `수정`, `PR 보냅니다`, `완료`
- 좋은 예: `feat: 이메일 로그인 화면 추가`, `fix: 회원가입 시 빈 비밀번호 허용 문제 해결`

### 본문 템플릿 (복사해서 쓰세요)

```markdown
## 무엇을 했나요?
- 로그인 화면(`LoginPage`) 컴포넌트를 추가했습니다.
- 이메일 형식이 유효하지 않으면 제출 버튼을 비활성화하도록 했습니다.

## 왜 했나요?
- 이슈 #12: 로그인 기능을 분리해 달라는 요청 반영

## 어떻게 확인하나요?
1. `npm run dev` 로 실행
2. 브라우저에서 `/login` 접속
3. 잘못된 이메일을 입력해 버튼이 비활성화되는지 확인

## 스크린샷 / 영상 (UI 변경이 있으면)
(이미지를 드래그해서 붙여 넣으시면 자동 업로드됩니다.)

## 체크리스트
- [x] 로컬에서 정상 동작 확인
- [x] 관련 문서 업데이트
- [ ] 단위 테스트 추가
```

팀에 따라 `.github/pull_request_template.md` 를 만들어 두면 PR 본문에 이 템플릿이 **자동으로 채워집니다**. 이는 나중에 심화 주제로 알아보시면 됩니다.

### 좋은 PR의 3가지 조건

1. **작다**: 한 PR에 한 주제만 담으세요. 500줄 넘어가면 리뷰어가 포기합니다.
2. **읽힌다**: 제목·본문만 봐도 **무엇을, 왜** 바꿨는지 이해됩니다.
3. **확인 가능하다**: 리뷰어가 코드를 받아 **실행/확인하는 방법**이 적혀 있습니다.

## 5.5 PR을 올린 뒤 — 리뷰 주고받기

PR을 만드신 뒤에는 저장소의 **Pull requests** 탭에서 목록을 보실 수 있습니다. 상단 탭은 다음을 구분합니다.

- **Conversation**: 논의와 커밋 요약
- **Commits**: 이 PR에 포함된 커밋 목록
- **Files changed**: 실제로 바뀐 파일의 diff (리뷰가 이루어지는 곳)

### 리뷰어가 하는 일

1. **Files changed** 에서 줄 왼쪽의 **+** 아이콘을 눌러 **특정 줄에 코멘트** 를 남깁니다.
2. 리뷰가 끝나면 오른쪽 위 **Review changes** 를 누르고 상태를 고릅니다.
   - **Comment**: 단순 의견, 승인/거절은 아님
   - **Approve**: "합쳐도 좋습니다"
   - **Request changes**: "이 부분은 고치신 뒤 다시 봤으면 해요"

### PR을 올린 사람이 하는 일

리뷰에서 수정 요청이 들어왔다면, 브랜치에서 **그대로 수정하고 다시 push** 하시면 됩니다. PR은 자동으로 갱신됩니다.

```bash
$ git switch feature/login
$ # 파일 수정
$ git add .
$ git commit -m "fix: 로그인 버튼 비활성 조건 보완"
$ git push
```

코멘트에는 이렇게 답글을 남겨 주시면 예의 바르고 추적도 편합니다.

- "말씀하신 부분, `LoginPage.tsx:42` 에서 수정했습니다. 다시 봐 주세요."
- "이 부분은 의도한 동작인데, 제가 설명이 부족했네요. 본문에 주석을 추가해 두었습니다."

## 5.6 리뷰 예절 — 신입생이 꼭 알아두실 것

### 리뷰를 **받는** 쪽 (PR 주인)

- 코멘트를 **개인 공격으로 받아들이지 않기**. 코드에 대한 의견이지, 나에 대한 평가가 아닙니다.
- 모든 코멘트에 답을 남겨 주세요. **"반영했습니다"** 한 줄이라도 있으면 리뷰어가 훨씬 편합니다.
- 동의하지 않는 코멘트는 **근거와 함께 반박**하셔도 됩니다. 오히려 좋은 토론이 됩니다.
- 리뷰가 한참 없으면 **정중히 핑**: *"시간 되실 때 가볍게 한 번 봐 주시면 감사하겠습니다 🙏"*

### 리뷰를 **해 주는** 쪽

- 사람이 아니라 **코드**에 대해 이야기하세요.
  - 🚫 "이걸 이렇게 짜시면 안 되죠."
  - ✅ "이 부분은 `null` 체크가 빠져 있어서 런타임 에러가 날 수 있을 것 같아요. 어떻게 생각하세요?"
- **칭찬도 함께**. 좋은 코드에는 👍 나 한 줄 코멘트를.
- 의견의 **강도**를 밝혀 주세요.
  - `nit:` (nitpick, 사소한 취향) → 반영 여부는 PR 주인이 결정
  - `(blocking)` → 반드시 고쳐야 합친다는 뜻
- 리뷰어가 구현까지 요구하지 않도록, **"이런 방향도 있어요"** 정도의 제안을 권장드립니다.

## 5.7 Draft PR과 빠른 피드백 루프

PR이 아직 완성되지 않았는데 **중간 점검**을 받고 싶으시다면 **Draft pull request** 를 활용하세요.

- PR 생성 화면 오른쪽 아래 `Create pull request` 버튼 옆 화살표 → **Create draft pull request**
- 상단에 **Draft** 라고 표시되고, merge 버튼은 비활성화됩니다.
- 준비가 되면 **Ready for review** 버튼으로 정식 PR로 승격시키시면 됩니다.

> 💡 혼자 실습 중이시라도, PR을 **나 자신에게** 올려 보시는 연습은 매우 유익합니다. "과거의 나"를 리뷰어로 두고 코드 리뷰를 해 보세요.

## 5.8 PR 합치기 (Merge)

리뷰가 승인되고 CI(자동 검사)가 통과되면, PR 하단의 초록색 버튼으로 합칠 수 있습니다. 세 가지 방식이 있습니다.

| 방식 | 이력 모양 | 언제 쓰나요? |
| --- | --- | --- |
| **Create a merge commit** | 브랜치 이력이 그대로 남고 병합 커밋 1개 추가 | 가장 기본. 히스토리 상세히 남기고 싶을 때 |
| **Squash and merge** | 여러 커밋이 **한 개**로 합쳐져 `main` 에 추가 | 커밋이 자잘할 때, 이력을 깔끔히 유지하고 싶을 때 (팀 프로젝트에서 많이 사용) |
| **Rebase and merge** | 병합 커밋 없이 선형적으로 이어 붙임 | 이력을 한 줄로 유지하고 싶을 때 |

팀의 규칙에 따르시면 되고, 처음에는 **Squash and merge** 를 권장드립니다. 깔끔합니다.

머지 후에는 **Delete branch** 버튼으로 작업 브랜치를 지우시고, 로컬에서도 정리해 주세요.

```bash
$ git switch main
$ git pull
$ git branch -d feature/login
```

## 자주 겪는 어려움

- **"PR을 올렸는데 `This branch has conflicts that must be resolved` 라고 떠요."**
  `main` 이 그사이 바뀌면서 내 브랜치와 충돌하고 있다는 뜻입니다. [6장 — 병합 충돌 해결](./06-merge-conflicts.md)에서 다룹니다.
- **"리뷰어로 등록하려는데 상대가 목록에 안 보여요."**
  해당 저장소에 **쓰기 권한** 이 있어야 리뷰어로 지정됩니다. `Settings → Collaborators` 에서 초대하셔야 합니다.
- **"제목을 바꾸고 싶어요."**
  PR 페이지 제목 옆 **Edit** 버튼을 누르시면 언제든 수정 가능합니다.
- **"실수로 PR을 너무 빨리 Merge 했어요."**
  `Revert` 버튼을 누르시면 방금 머지한 내용을 되돌리는 **새로운 PR** 이 자동 생성됩니다.
